# FeatherTalk Rust 桌面版迁移设计

日期：2026-11-17

状态：方案 B 已选定；独立可实施性审阅未发现重要缺口；设计待确认；尚未开始产品代码实现。

## 1. 目的与已确认需求

在现有 `feather-talk-gui` 中，以 Rust + Tauri + React 实现 FeatherTalk 的完整本地工作流。神经网络、自动微分和优化器使用 Burn，安装后的应用不依赖 Python/PyTorch 环境。

用户已确认：

- 同时迁移人物训练与推理，包括必需的视频预处理。
- NVIDIA、AMD、Intel Arc、Apple Silicon 和 CPU 均需能完成训练与推理。GPU 支持必须验证计算确实发生在对应 GPU 上。
- Apple Silicon 使用 GPU；Intel Mac 使用 CPU。
- 首版仅支持默认 FeatherTalk 人物视觉网络，人物只接受一段训练视频。
- 人物从头训练，仅使用新版本的 Burn 模型与训练状态格式；以后可增加旧 Python 人物模型导入。
- 首版是导入音频、导出视频；为后续实时音频驱动保留扩展边界。
- 首次运行允许联网下载模型及组件，准备完成后可以离线工作。
- 同一时间只执行一个训练或生成任务。
- 提供一键流程，同时允许在高级选项中配置 epoch、batch size 等参数。
- 页面实时显示 loss 曲线；失败时提供原因与排查方向。
- 性能目标是保持效果的前提下尽可能快，目前没有具体耗时或 FPS 门槛。
- 用户选择方案 B：按硬件选择和调优后端。

本轮未承诺一个新的训练算法。以当前 Python 仓库的模型、预处理约定和损失函数作为迁移基线，效果基线是相近的口型、画质与帧间稳定性。该效果验收建议尚待本设计一起确认。

首版不包含 MobileOne 人物网络、多视频合训、旧人物 `.pth` 导入、实时采集与播放、并行训练/生成、多卡分布式训练和云端计算服务。PFLD 内部使用的 MobileOne/GhostOne 结构仍须实现，它属于预处理模型，与排除的 MobileOne 人物网络不同。

## 2. 当前代码与模型审计

参考代码位于同级 `../FeatherTalk`：

| 部分 | 当前实现 | 迁移要求 |
| --- | --- | --- |
| 预处理 | `data_utils/process.py`、`get_landmark.py`、`detect_face.py` | 音视频解码、抽帧、检测、关键点、音频特征 |
| 公共音频编码器 | `data_utils/feather_hubert/feather_hubert.py` | 参数化配置、16 kHz 输入、特征帧数与归一化约定 |
| 人物视觉网络 | `model.py` 中的 `Model` | AudioAdapter、注意力融合、UNet 编解码、144×144 输出 |
| 数据集与裁切 | `face_utils.py`、`dataset_mouth_roi.py` | 相邻帧对、共享参考帧、嘴部掩码、音频窗口与边界 |
| 训练 | `train.py` | Adam、全部现有损失、检查点、续训 |
| 离线生成 | `inference.py` | 25 FPS、资源帧往返选择、预测回贴、音视频封装 |
| GUI | Tauri 2 + React 初始模板 | 尚无业务功能或 Burn 依赖 |

`../models` 仅有四组 SafeTensors 权重及 manifest，尚无已验证的 Burn 网络实现。权重格式转换不等于网络前向、梯度或训练正确性已验证。

- FeatherHuBERT：manifest 来源为 `feather_hubert_188_latest_99.pth`，SHA-256 为 `58df96af118d75d7f69da441e1f3960096f28dda637a4e8f4265f108d27aeb52`。当前 Python 仓库的 `feather_hubert.pth` 为 `3b147e66502132bac3ff76b4730c2a83c341c75251d22a28182a5a1b689cfc46`。旧来源文件与转换脚本已丢失，须按当前原权重重新生成转换资产与验证记录。188/144 的含义和兼容性以 checkpoint 配置、网络定义及张量形状核验为准。
- SCRFD：当前原始 ONNX 哈希与 manifest 一致；manifest 提及的生成源码 `scrfd_2_5g.rs` 不在仓库中。需要重新生成或重建网络，并验证输出和检测后处理。
- PFLD：当前 `checkpoint_epoch_335.pth.tar` 哈希与 manifest 一致。需实现对应 GhostOne 网络并确认训练分支/部署分支对应关系。
- VGG19：已有 conv3_3 子网络权重，需要验证层号、颜色、数值范围与原版一致。参数冻结，但生成图像经过 VGG 的输入梯度必须保留。

当前 Python 源码中的 FeatherHuBERT 默认配置与模型 manifest 的配置存在差别；实际使用参数必须从当前 checkpoint 配置读取，不能直接套用类的默认值。当前主机的 `python` 命令不可用；参考验证所需的开发环境在实施阶段准备，不随产品分发。

## 3. 方案比较与选择

| 方案 | 实现 | 取舍 |
| --- | --- | --- |
| A：统一后端 | GPU 统一使用 WGPU，另提供 CPU 后端 | 后端适配、构建与维护较集中 |
| B：按硬件调优 | NVIDIA 比较 CUDA 与 Vulkan；AMD、Arc 使用 Vulkan；Apple Silicon 使用 Metal；CPU 单独调优 | 有更多性能选择，需要更多构建、验证和诊断工作 |

用户选择 B，原因是希望在同等效果下尽可能快。B 不预设 CUDA 一定比 Vulkan 快，自动选择依据正确性与整条工作流实测，用户也能明确指定设备和后端。

官方当前文档显示 Burn 0.22.1 提供 CUDA、ROCm、Vulkan、Metal、WGPU、CubeCL CPU 和 Flex CPU，并提供自动微分与融合能力。旧转换记录中的 Burn 0.21.0 不能直接视为新实现的固定依赖。实现初期以 0.22.1 为候选版本，完成关键算子与存储验证后锁定精确版本；如必须换版本，要记录技术原因并重新生成相关验证结果。

参考：[Burn 后端与功能](https://docs.rs/burn/0.22.1/burn/)、[Burn 训练后端示例](https://burn.dev/books/burn/basic-workflow/backend.html)。

## 4. 结构与职责

以下为实现方提出的结构，随本设计确认：

```text
React 页面
  └─ Tauri 命令、事件与任务管理
       └─ Rust worker 进程（一次一个重任务）
            ├─ Burn 模型、训练与推理
            ├─ 数据加载、预处理与有界缓存
            └─ FFmpeg / FFprobe 音视频组件
```

- `src/`：人物项目、训练、视频生成与资源/设备设置界面。
- `src-tauri/`：应用生命周期、文件选择、任务状态、资源管理、worker 启停及事件转发；不直接承担模型计算。
- `crates/feathertalk-core/`：配置、项目与模型元数据、任务协议、结构化错误；不依赖 Tauri。
- `crates/feathertalk-engine/`：Burn 模型、数据集、损失、优化器、媒体适配、设备能力与性能策略。先按模块组织，确有依赖边界需要再拆 crate。
- `crates/feathertalk-worker/`：独立进程入口；根据目标平台和后端 feature 构建对应组件。
- `tools/`：公共模型转换、Python 参考输出生成、数值对齐与基准工具；它们是开发工具，不属于最终应用运行依赖。

worker 隔离 GPU 计算，便于在进程异常退出后继续显示失败原因、日志与恢复入口。控制与指标使用带协议版本和任务 ID 的本地结构化消息；大块图像与音频不经前端 JSON 事件传输。标准错误保留组件日志，标准输出仅承载协议消息。Windows 后台组件隐藏控制台窗口。

CPU、Vulkan/Metal 与 CUDA 可按平台分为不同 worker 构建，避免把所有后端依赖强加到每一种安装包中。首启资源管理器下载本机需要的组件。CPU worker 始终可用。

## 5. 设备策略与验证范围

| 设备类别 | 候选执行路径 | 必须验证 |
| --- | --- | --- |
| Windows/Linux NVIDIA | CUDA 与 Vulkan 比较 | 前向、反向、原损失训练、续训、视频导出 |
| Windows/Linux AMD | Vulkan；特定硬件未来可再评估 ROCm | 同上 |
| Windows/Linux Intel Arc | Vulkan | 同上 |
| Apple Silicon Mac | Metal | 同上 |
| Windows/Linux CPU、Intel Mac CPU | Burn CPU 后端；比较适用的 CPU 实现 | 同上 |

本机可识别 Windows + RTX 2060；用户另外提供 Win11 + Arc B580。CPU 可直接测试。Linux、AMD、Apple Silicon 与 Intel Mac 实机验证环境尚待补齐。支持目标保持完整；构建通过、框架声称支持和实机验证通过必须分别记录，不能把 CPU 运行结果计作对应 GPU 验收结果。

首轮打包验证建议基线为 Win11 x86_64、Ubuntu 24.04 x86_64、macOS 13+ arm64 与 x86_64。此处是实现方建议，不代表用户已决定最低系统版本。最终支持下限由依赖和实机验证固定，作为安装包要求公布。

自动选择设备时，先确认驱动可用、完整算子路径可运行、梯度正确与内存预算满足，再比较候选后端。缓存基准结果时绑定设备、驱动、模型、引擎版本与精度。页面始终显示实际设备、后端、精度和实际 batch size。GPU 不可用时给出原因及 CPU 选择入口，明确显示最终执行设备。

## 6. 项目与一键工作流

一个人物对应一个项目目录和一段素材视频，可以管理多个独立人物项目。

```text
创建人物 → 选择一段视频 → 检查素材与资源
         → 预处理 → 训练 → 保存人物模型
选择人物 → 导入音频 → 选择输出位置 → 生成与导出视频
```

实现方建议的输入行为：保留原素材，生成项目内的 25 FPS 恒定帧率副本；音频按原版约定准备为 16 kHz 输入。声道选择、波形归一化、特征帧数、两 token 对一视频帧的分组和边界补零均需与参考实现明确对齐。非 25 FPS 素材的自动规范化是 GUI 的便利功能，验证时使用同一规范化副本作为 Python/Rust 共同输入。

保留以下数学与图像协议：152×152 人脸裁切、中心 144×144、现有嘴部掩码、BGR 数值/通道约定、原版插值和坐标取整语义、40×1024 音频窗口、相邻帧对共享参考图。尤其要验证双线性上采样的 `align_corners=True`、padding 和 OpenCV 面积缩放语义；不能只匹配输出形状。

预处理按素材哈希、预处理版本和公共模型哈希建立缓存。公共音频模型变化必须使旧音频特征缓存失效。检测失败要定位到视频时间/帧号；不通过静默丢帧破坏音画对齐。具体可恢复坏帧策略由实施时的参考行为核验决定，默认先给出明确错误。

首版输出建议固定为 25 FPS MP4、H.264 视频与 AAC 音频，保留素材画幅与原版回贴行为。先使用稳定的软件编码路径；硬件编码作为经过质量和兼容性验证后的可选优化。

## 7. 训练、检查点与任务控制

一键训练默认沿用当前 `train.py` 的超参数：60 epochs、目标 batch size 8、Adam 学习率 0.001、每 5 epochs 定期保存。Adam 的 beta1=0.9、beta2=0.999、epsilon=1e-8、weight decay=0，显式匹配 PyTorch 默认语义，不直接依赖 Burn 的默认值；归一化层的 epsilon、运行统计更新和训练/推理行为同样需核对。batch size 指相邻帧对数量，内部展开后包含两倍视频帧。

高级选项提供 epoch 总数、batch size、学习率、保存间隔、随机种子和数据加载设置；损失权重与时序/嘴部参数放在进一步展开的选项中，默认匹配当前 Python 代码：

| 项目 | 默认值 |
| --- | --- |
| 全图 L1 | 系数 1 |
| 嘴部 L1 | 4.0 |
| 时序差分 | 0.5 |
| 嘴部时序差分 | 4.0 |
| VGG 感知 MSE | 0.01 |
| 嘴部梯度损失 | 0.5 |
| 时序低通核 / 步长 | 5 / 1 |

一键模式可在正式训练前通过完整训练步探测可用 batch size，最大不超过默认目标；探测包含 VGG 生成分支的反向路径。探测过程还原参数、优化器、BN 与随机状态，不能把试运行当作正式训练步。高级模式明确指定 batch size 时保留用户设置，内存不足则提示调整建议。

单任务状态包括排队/准备、预处理、训练、生成、保存/封装、完成、取消、失败。下载与设备检查属于准备阶段。前端响应不依赖重任务完成，任务事件均带任务 ID，避免迟到事件污染下一个任务。

训练提供取消并保存、定期检查点和从 Burn 检查点续训。取消请求在当前完整训练步结束后处理；已经提交的检查点保持可读。生成取消后保留既有成功输出，并清理本次未完成的临时输出。

版本化检查点保存网络参数与 BN 状态、优化器状态、epoch/global step、采样进度与随机状态、超参数、素材及预处理指纹。数据采样和随机参考帧选择需可从保存的状态恢复，防止预取队列影响续训进度。支持相同模型在不同已支持设备之间加载和续训；不要求跨硬件逐位一致。`epochs` 表示总轮数。

检查点采用 Burn 原生记录与 JSON manifest，使用暂存写入及原子提交，区分可续训检查点和用于推理的人物资源。精确文件布局和 Burn 存储 API 的使用由实现者在锁定版本后决定，但所有必需状态必须可往返恢复。旧 `.pth` 导入将来通过独立 importer 转换为同一版本化人物资源，当前页面不提供虚假导入入口。

## 8. 前端与错误反馈

功能布局建议如下，视觉细节留给实现者：

```text
人物项目 | 训练 | 视频生成 | 资源与设备

训练：人物与素材、开始/续训、可展开高级选项
      当前阶段、epoch/step、实际设备、耗时与进度
      实时总 loss 曲线 → 可展开分项 loss
      取消并保存、错误说明、详细日志

生成：人物、音频、输出位置、生成按钮
      当前阶段、生成进度、完成视频与打开目录
```

默认界面展示总 loss，展开后展示各分项、学习率与必要训练指标。worker 记录带 `global_step` 和 epoch 的指标，向 UI 的推送上限建议为每秒 2 次，避免绘图与读回损失值成为训练瓶颈。保存采样后的历史指标，重启或重新打开项目后能恢复曲线。长任务的曲线在前端降采样显示，保存值不跟随显示降采样丢失。

结构化错误包含任务阶段、错误码、实际错误证据、用户说明、可执行的排查建议和日志位置。重点覆盖：资源下载/哈希失败、驱动/后端初始化失败、显存或内存不足、算子/精度不支持、无有效人脸、素材无音轨、编码失败、磁盘不足和路径权限问题。不能把所有异常归为显存不足；无法确定原因时展示已知阶段和原始错误。

例：显存不足提示当前设备、batch size，建议减小 batch size 或选择 CPU；资源校验失败提供重新下载入口；人脸检测失败定位素材时间并提示检查遮挡、主体和画面。详细日志可复制，不包含前端需要猜测的错误分类。

## 9. 资源下载与离线运行

资源清单为各平台组件与公共模型记录版本、文件大小、SHA-256、源地址、架构标识、最低引擎版本和来源说明。下载显示进度，使用暂存文件，校验通过后才提交到用户资源目录；失败可重试，不破坏已有可用版本。中断下载的恢复能力由 HTTP 服务能力决定，至少能够安全重新下载。

公共模型、worker 和媒体组件均有本地就绪检查。全部必需资源准备完毕后，训练、模型加载、检查点续训和视频导出不能隐式访问网络。升级资源应显式触发并保留项目所需的既有版本。开发阶段可从当前本地 `models` 和本地组件目录导入同一资源缓存。

生产下载地址/托管方式尚未提供，是发布前需要落实的外部配置，不阻塞本地实现和验证。现有 PFLD/SCRFD manifest 标记 `redistribution_approved: false`，其他公共权重来源说明也未确认再分发许可，因此不能直接把现有权重当作已批准的公开下载包。发布资源时应补齐来源与分发依据，或配置获准的上游获取方式。FFmpeg 构建与实际包含的编解码器也需有对应构建信息与 notices。此项来自现有资产记录，不是对本地使用的新增限制。

## 10. 性能策略

先建立 FP32 的正确性与完整训练基线，再启用能证明效果保持且端到端有收益的优化：

- 公共音频特征一次提取复用，训练裁切、关键点和掩码缓存；CPU 预处理与数据预取使用有界队列。
- 相同素材帧的静态视觉编码可以在数学等价且资源预算允许时缓存；按场景使用有界 CPU/磁盘缓存或按需 GPU 缓存，避免默认把整段视频全部驻留显存。
- 离线推理批处理，保持帧顺序与正确音频窗口；尽量减少 CPU/GPU 往返。
- 按设备比较 CUDA/Vulkan 或合适的 CPU 执行路径，测试算子融合、内核缓存与自动调优。
- 混合精度需验证梯度、归一化、损失、检查点和效果；不预先承诺所有设备都支持同一种低精度训练方式。
- 固定相同输入、模型和 batch size 比较后端；将首次编译/调优冷启动耗时与热运行耗时分别报告。额外给出设备可用最大 batch 下的吞吐，避免把 batch 变化误认为纯后端收益。

RTX 2060、Arc B580 和 CPU 分别记录预处理耗时、训练 steps/s 或帧/s、峰值内存/显存、特征提取速度、视觉推理速度及完整视频导出耗时。完整流程指标优先于单算子宣传数据。

## 11. 实时扩展边界

将音频来源、带时间信息的特征、人物帧生成和输出接收端分开。当前提供文件来源和视频文件输出；未来可增加带时间戳的音频块来源与播放接收端，并加入有界队列、背压、取消、结束/flush 和会话重置。

离线管线与核心计算都不依赖 React/Tauri。实时扩展无需把模型逻辑搬出 GUI 命令处理器，也无需更换项目/模型元数据格式。

当前模型使用前后音频上下文，音频处理还存在整段统计/时间维归一化。因此预留接口并不等于当前模型天然支持低延迟流式或与离线输出逐点相同。实时模式的窗口、未来上下文、缓冲延迟和必要算法适配留待该功能设计与验证；首版不展示实时按钮或作实时性能承诺。

## 12. 验证与完成标准

### 数值与训练

1. 为当前公共原权重和代表性输入生成可重复的 Python/ONNX 参考输出，记录源哈希、配置和工具版本。
2. 四个公共模型验证形状、关键中间层与最终输出；SCRFD 另验证解码/NMS，PFLD 另验证坐标映射。验证阈值在观察 FP32 基线后按算子误差设定并固定，禁止为掩盖错误而任意放宽。
3. 用同一组人为固定的 FeatherTalk 参数与输入比较前向、全部损失项及代表性梯度；含上采样、归一化、注意力、VGG 生成分支的反向验证。
4. 对所有目标执行路径完成一个完整训练步、短程过拟合和检查点往返/续训验证。损失有限且梯度有效，非仅“程序没崩溃”。

### 工作流与效果

使用同一人物视频和驱动音频，对 Python 与 Rust 使用一致的规范化输入，比较预处理、音画时长、回贴与口型、画质、帧间稳定性。训练具有随机性，不把跨框架 loss 数值逐步相同当作收敛标准。当前尚未指定一套验收素材；实施早期要固定合法可用的测试素材与参考产物，形成可重放基准。

完整验收覆盖新建人物、一键训练、高级参数、曲线实时与历史恢复、取消并保存、重启续训、导出播放、失败诊断、资源下载失败重试及断网后的完整流程。驱动丢失、显存不足、worker 异常退出、中文/空格路径和输出中断至少有针对性验证。

### 平台交付

每个发布目标需完成构建与安装验证；每个声称支持的硬件路径需有实际执行设备记录和训练/推理结果。RTX 2060、B580、CPU 先完成现有环境实测，其他平台通过补充测试环境完成相同验收，缺失结果明确保持待验证。生产资源地址与可分发资产准备好后，执行一次干净环境首启下载、断网训练和导出验证。

## 13. 实施顺序与实现者可决定事项

实施顺序建议：资产/原权重审计 → Burn 关键算子及前反向可行性 → 公共模型和人物网络对齐 → CPU/RTX 2060/B580 完整训练生成 → 任务 worker 与桌面流程 → 资源交付 → 其余平台验收 → 经测量的性能优化。最终仍交付全部目标范围，阶段划分不缩减支持目标。

实现者可决定具体依赖、IPC 编码/分帧、图表库、模块拆分、检查点物理布局、缓存上限及视觉样式；这些决定要遵守上述功能、正确性、离线与可观测性约束。GPU 算子缺失时可实现和验证 Burn/CubeCL 扩展，不能通过删除损失、换人物网络或整条路径切到 CPU 来宣称相应 GPU 迁移完成。

用户需要审核的实现方建议：worker 进程隔离、输入自动规范化为 25 FPS、FP32 效果基线、默认参数与自动 batch 探测、平台首轮验收基线。生产下载资源与其他平台测试环境属于尚待落实的发布依赖。
