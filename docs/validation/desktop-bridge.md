# Desktop service validation

The Tauri process owns the project index, local resource cache and one active task. It does not link Burn. A worker receives one accepted project binding when a task starts; opening a different project does not affect that binding. A discovery worker uses a projectless Hello/Ready session and rejects Start.

- `cargo test --offline --locked -p feather-talk-gui -p feathertalk-core --lib --tests` covers the desktop service, host, resource cache and Rust contracts. The project tests cover moving a Unicode directory while preserving `project.json`, damaged content, exclusive task ownership, reconnect and cancellation. Service-level history tests use record offsets for a single run and reject a torn tail or a path outside the project.
- `cargo test --offline --locked -p feathertalk-worker` covers the raw protocol. The discovery test checks the real CPU worker's device report and verifies that a direct Start request is rejected without a task event.
- `pnpm test:contracts` checks the same JSON fixture as Rust, including the frontend's command arguments, exact JavaScript seed range, and a terminal notification arriving during the snapshot read. A later worker's lower sequence numbers are accepted under its new task ID. `pnpm build` and `cargo check --offline --locked -p feather-talk-gui` check the two build boundaries.

The app uses `tauri::path::app_local_data_dir()` for `projects.json`, `resources` and a trusted `resource-catalog.json`. A debug build can use a separate absolute `FT_DESKTOP_DATA_DIR`. With no local catalog, it falls back to the development metadata, whose missing runtime pins and URLs are intentional. Build and package both worker and probe from the current source as described in [the resource guide](../../resources/README.md); an older worker that lacks the discovery prelude is not sufficient for this desktop bridge. Importing a local manifest can only install an exact package already listed in the configured catalog.

On Windows the native WebView test used local, verified CUDA packages and a copy of the two-step project from [installed worker validation](installed-worker.md). It called the same Tauri commands as the React client. The first package import reported incomplete inventory; both imports together reported ready. The application discovered the RTX 2060 before opening any project and read the relocated project's history. It rejected a second job while generation was active and exported a three-frame 640×600 H.264/AAC MP4 at 25 fps in a Unicode directory. In the WebView, an ungranted request for the MP4 returned 403, and a request for another project's preview was rejected. After the correct project and task were authorized, a video range request returned 206 and the WebView decoded the 640×600 video (0.12 s). A new CUDA worker resumed the same run from step 2. The WebView received step 3's finite loss, `CheckpointCommitted` and one terminal event, and the reloaded project index named the new checkpoint.

This is a debug test with a derived fixture and prepositioned resources. It does not certify distribution, OS-level offline operation, video quality on real footage, or rendering on Linux and macOS.
